# 故障排查手册

**使用方法**：按现象查编号，按「排查命令」顺序执行，不要跳步。

排查通用顺序：**进程 → 端口 → 日志 → 资源 → 网络 → 配置**。
先确定是哪一层出了问题，再深入，不要一上来就改配置。

---

## F01 应用容器起不来，`docker compose ps` 显示 Exited

**现象**：`app` 状态是 `Exited (1)`，访问 502 或连接拒绝。

**常见原因**

1. `.env` 里 `DATABASE_URL` 写错（最常见）
2. 数据库还没起来就连了
3. `JWT_SECRET` 为空

**排查**

```bash
docker compose logs --tail 50 app
```

- 看到 `could not translate host name "db"` → DATABASE_URL 的主机名写错了
- 看到 `password authentication failed` → 密码和 db 服务的不一致
- 看到 `Connection refused` → 数据库没起，先 `docker compose up -d db`

**处理**

```bash
grep DATABASE_URL .env        # 必须是 ...@db:5432/docqa，不是 localhost
docker compose up -d db && sleep 10 && docker compose up -d app
```

## F02 数据库容器反复重启

**现象**：`db` 状态在 `Restarting` 之间反复跳。

**原因**

1. 磁盘满了（见 F09）
2. 数据目录权限不对（`pgdata` 卷被别的用户改过）
3. `POSTGRES_PASSWORD` 改了，但数据卷里还是旧密码

**排查**

```bash
docker compose logs --tail 50 db
df -h /
```

**处理**

改过密码导致的：

```bash
docker compose down
docker volume rm doc-qa-service_pgdata     # 数据会丢，先确认有备份
docker compose up -d db
```

**警告**：这是删库操作。执行前必须确认已有 `pg_dump` 备份，并向客户书面确认。

## F03 页面 502 Bad Gateway

**现象**：nginx 返回 502，容器都在跑。

**原因**：nginx 连不上 `app`，说明 app 进程挂了或端口没监听。

**排查**

```bash
docker compose ps app                        # 是否 running / healthy
docker compose exec nginx ping -c 2 app      # 网络通不通
docker compose exec app curl -s localhost:8000/healthz
```

**处理**

- `app` 不 healthy → 转 F01 看日志
- 网络不通 → 两个容器不在同一网络，检查 `docker-compose.yml` 没有被改乱
- app 正常但 nginx 502 → `docker compose restart nginx`

## F04 上传文件返回 413

**现象**：`Request Entity Too Large`。

**原因**：nginx 的 `client_max_body_size` 是 25m，应用侧 `MAX_UPLOAD_MB` 是 20m，超了就拒。

**处理**

两处都要改，只改一处没用：

```bash
# 1. nginx/nginx.conf
client_max_body_size 60m;

# 2. .env
MAX_UPLOAD_MB=50
```

```bash
docker compose restart nginx && docker compose up -d app
```

## F05 文档一直停在 pending

**现象**：上传成功，状态永远 `pending`，不变成 `ready`。

**原因**：`worker` 没在跑，或它连不上数据库。

**排查**

```bash
docker compose ps worker
docker compose logs --tail 50 worker
```

- 日志里有 `worker started, polling every 2.0s` → worker 正常，看是不是积压太多
- 没有这行 → worker 没启动或崩了

**处理**

```bash
docker compose up -d worker
docker compose logs -f worker        # 应能看到 claiming / indexed 日志
```

如果 worker 在跑但没日志输出，说明它查不到 pending 任务——检查它和 app 连的是不是同一个数据库。

## F06 文档状态变成 failed

**现象**：`status: failed`，`error` 字段有原因。

**常见 error 与处理**

| error 内容 | 原因 | 处理 |
|---|---|---|
| `没有提取到可用的文本内容` | 扫描版 PDF，没有文字层 | 让客户提供文字版，或先做 OCR |
| `FileNotFoundError` | 上传目录的卷没挂上 | 检查 compose 里 `uploads` 卷 |
| `expected N dimensions` | 换过 embedding 模型 | 见 F08 的处理 |
| `could not connect` | worker 连不上数据库 | 转 F01 |

**排查**

```bash
curl -s "http://localhost/api/v1/documents/{id}" -H "Authorization: Bearer $TOKEN"
docker compose logs --tail 50 worker | grep -i error
```

## F07 所有接口返回 401

**现象**：带着 token 也返回 401，`code` 是 `UNAUTHORIZED`。

**原因**

1. token 过期（默认 720 分钟）
2. 服务端改过 `JWT_SECRET`，旧 token 全部失效
3. 请求头没带 `Bearer ` 前缀

**排查**

```bash
curl -s -X POST http://localhost/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"test@example.com","password":"12345678"}'
```

能拿到新 token → 原 token 过期了，正常重新登录。
拿不到 → 密码错，或用户不存在，查 `SELECT id,email FROM users;`。

## F08 问什么都说"文档中没有找到相关内容"

**现象**：文档状态是 ready，但所有问题都拒答。

**原因**（按概率排序）

1. `ANSWER_THRESHOLD` 设太高（换模型后没重新标定，最常见）
2. 向量维度和模型不匹配，检索结果全是垃圾
3. 用户 A 的文档，用户 B 在问（数据按 `owner_id` 隔离）
4. 文档内容确实没有答案

**排查**

```bash
# 看 top1 相似度，正常应该在 0.3 以上
curl -s -X POST http://localhost/api/v1/qa/ask \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"question":"年假有几天？","top_k":3}'
```

- `citations[0].score` 在 0.05 到 0.2 之间 → 可能是阈值问题，或向量不匹配
- `citations` 为空 → 该用户名下没有 ready 的文档

**处理**

```bash
# 1. 临时降低阈值验证
sed -i 's/ANSWER_THRESHOLD=.*/ANSWER_THRESHOLD=0.05/' .env
docker compose up -d app

# 2. 如果降阈值后还是不相关，说明向量维度或模型错了 —— 必须重建索引
docker compose down -v          # 清空数据，慎用
docker compose up -d
# 重新上传全部文档
```

**标定阈值的方法**：改 `.env` 里的值 → 重启 app → 跑 `python scripts/eval_qa.py`，
看「误拒率」和「编造率」两条曲线的交叉点，取平衡值。没有测试集就没有结论。

## F09 磁盘写满

**现象**：`No space left on device`，数据库或应用崩溃。

**排查**

```bash
df -h /
docker system df
du -sh /var/lib/docker/containers/* 2>/dev/null | sort -h | tail -5
```

**处理**

```bash
# 1. 清理日志（最常见）
truncate -s 0 /var/lib/docker/containers/*/*-json.log

# 2. 清理无用镜像
docker image prune -af

# 3. 清理构建缓存
docker builder prune -af

# 4. 清理旧备份
find /backup -name "*.sql.gz" -mtime +14 -delete
```

**根因预防**：配 docker 日志轮转，见《运维手册》6.1。不配的话每隔几个月必然复发一次。

## F10 时间不对 / 中文乱码

**现象**：日志时间差 8 小时，或导出的中文变问号。

**原因**：容器时区是 UTC，或 locale 没设。

**处理**

`docker-compose.yml` 里已给 db 配了 `TZ: Asia/Shanghai`，应用镜像也设了同样的值。如果还是不对：

```bash
docker compose exec app date                # 看容器时间
docker compose exec db psql -U docqa -c "SHOW timezone;"
```

不一致的话，检查是不是用了旧的镜像（`docker compose build --no-cache`）。

中文文件名乱码通常是宿主机 locale 问题，上传前确认 `echo $LANG` 是 `UTF-8`。

## F11 重启后数据没了

**现象**：`docker compose restart` 后文档列表空了。

**原因**：用了 `docker compose down -v`，`-v` 会删掉命名卷。或者 compose 文件里的 volumes 被删了。

**处理**

从备份恢复，见《运维手册》第 5 节。

**教训**：`down -v` 等于删库，任何时候都要先备份。这条必须写进客户的操作规范。

## F12 80 端口被占用

**现象**：`bind: address already in use`。

**排查**

```bash
ss -lntp | grep ':80 '
```

**处理**

两个选择：

```bash
# 方案 A：停掉占用端口的服务（通常是系统自带的 nginx 或 apache）
systemctl stop nginx

# 方案 B：换端口，改 docker-compose.yml
ports:
  - "8080:80"
```

## F13 内存不足，容器被 OOM Killer 杀掉

**现象**：`app` 或 `db` 突然 Exited，日志末尾没有异常，`dmesg` 里有 `Out of memory`。

**排查**

```bash
free -h
dmesg | tail -20 | grep -i "killed process"
```

**处理**

```bash
# 限制 pg 内存占用，加到 docker-compose.yml 的 db 服务
command: postgres -c shared_buffers=256MB -c max_connections=50
```

8G 内存的机器上，PostgreSQL 默认配置过于保守但也别乱调：
`shared_buffers` 给 1/4 内存，`max_connections` 不超过 100。

## F14 点 Docker Desktop 的 Start 按钮起不来

**现象**

在 Docker Desktop 的 Containers 页面点项目行的启动按钮，弹出：

```
Cannot start Docker Compose application. Reason: compose [start] process exited with exit code 1
Container doc-qa-service-db-1 Starting ... Started ... Waiting ...
Error dependency db failed to start
dependency failed to start: container doc-qa-service-db-1 exited (0)
```

但用命令行 `docker compose up -d` 完全正常。

**原因**

Docker Desktop 的启动按钮内部执行的是 `docker compose start`。
`start` 只负责把已存在的容器拉起来，**不会等待 `depends_on` 里的 `condition: service_healthy`**——
它不会等 db 的健康检查通过，就往下走；db 因为被判定"依赖失败"而收到停止信号，
日志里表现为 `received fast shutdown request` 后 `exited (0)`。

正常退出码 0 会让人误以为数据库坏了，其实没坏，是被叫停的。

**排查**

```bash
docker compose logs --tail 30 db
```

看到这几行就是本例：

```
LOG:  database system is ready to accept connections
LOG:  received fast shutdown request      ← 起来 2 秒后被叫停
LOG:  database system is shut down
```

**处理**

不要用图形界面的启动按钮，用命令行：

```bash
docker compose up -d
```

`up` 会按 `depends_on` 的条件等 db 真正 healthy 之后才启动 app。
启动完确认一下：

```bash
docker compose ps
curl -s localhost/healthz
```

**延伸**：图形界面适合看状态和日志，不适合管这种有启动顺序依赖的多容器项目。
客户现场的标准化操作也统一用命令行，避免"点一下就行了"变成"点一下怎么又挂了"。

## 附：一次性收集现场信息的脚本

出问题先跑这个，把输出发给支持，比描述现象有效十倍：

```bash
#!/usr/bin/env bash
echo "===== 时间 ====="; date
echo "===== 容器 ====="; docker compose ps
echo "===== 资源 ====="; free -h; df -h /
echo "===== 探针 ====="; curl -s localhost/healthz; echo; curl -s localhost/readyz; echo
echo "===== app 日志 ====="; docker compose logs --tail 50 app
echo "===== worker 日志 ====="; docker compose logs --tail 50 worker
echo "===== db 日志 ====="; docker compose logs --tail 30 db
```
