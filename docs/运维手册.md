# 运维手册

面向对象：客户运维人员 / 一线支持
服务端口：80（nginx）→ 8000（应用）

---

## 1. 服务组成

| 服务 | 作用 | 挂了会怎样 |
|---|---|---|
| `nginx` | 反向代理、限流、入口 | 全站不可访问 |
| `app` | HTTP 接口 | 全站不可访问 |
| `worker` | 文档解析与向量化 | 页面能开，但新文档永远卡在 pending |
| `db` | PostgreSQL + pgvector | 全站不可访问，数据全在这里 |

**关键认知**：`worker` 挂了不会报错，只会静默积压。巡检必须单独看它。

---

## 2. 日常启停

```bash
cd /opt/doc-qa-service      # 实际部署目录

docker compose ps                 # 看状态
docker compose restart app        # 重启应用（不影响数据库）
docker compose stop               # 停止全部
docker compose up -d              # 启动全部

./scripts/deploy.sh               # 重新部署（会重新构建）
./scripts/rollback.sh v0.1.0      # 回滚到指定版本
```

**顺序原则**：先起 db，等 healthy，再起 app/worker，最后 nginx。`deploy.sh` 已经按这个顺序做了，不要手动乱起。

---

## 3. 日志

```bash
docker compose logs -f app --tail 100      # 应用实时日志
docker compose logs -f worker              # 任务日志
docker compose logs --tail 200 nginx       # 访问日志
docker compose logs --since 30m app        # 最近 30 分钟
```

应用日志是 JSON 格式，每条都带 `request_id`。用户报错时先要 `x-request-id` 响应头，然后：

```bash
docker compose logs app | grep '<request_id>'
```

能一把捞出这个请求的所有日志，包括耗时、状态码、异常栈。

**日志会被 docker 无限堆积**，必须配轮转，见第 6 节。

## 4. 配置变更

配置全在 `.env`，改完必须重启对应服务：

```bash
vi .env
docker compose up -d app worker     # 配置变了要重建容器，restart 不生效
```

常见变更：

| 变更 | 影响 | 注意 |
|---|---|---|
| `ANSWER_THRESHOLD` 调高 | 拒答变多，编造变少 | 改完跑 `eval_qa.py` 看指标 |
| 换 `EMBEDDING_MODEL` / `EMBEDDING_DIM` | 向量维度变 | **必须清空 chunks 重新索引** |
| 改 `JWT_SECRET` | 所有已登录用户失效 | 提前通知 |
| 改 `CHUNK_SIZE` | 只影响新上传的文档 | 老文档要重传 |

## 5. 备份与恢复

**备份（建议每日凌晨）：**

```bash
docker compose exec -T db pg_dump -U docqa docqa | gzip > backup-$(date +%F).sql.gz
docker run --rm -v doc-qa-service_uploads:/data -v $(pwd):/backup alpine \
  tar czf /backup/uploads-$(date +%F).tar.gz -C /data .
```

数据库和上传文件必须一起备。只备份数据库，恢复后文档记录在、原文件没了，全部变成 failed。

**恢复：**

```bash
gunzip -c backup-2026-11-01.sql.gz | docker compose exec -T db psql -U docqa docqa
docker run --rm -v doc-qa-service_uploads:/data -v $(pwd):/backup alpine \
  tar xzf /backup/uploads-2026-11-01.tar.gz -C /data
docker compose restart app worker
```

**恢复演练**：交付时必须实际演练一次，记下耗时。没演练过的备份等于没备份。

## 6. 必须配的三件事

**6.1 日志轮转**（不配迟早磁盘写满）

```bash
cat > /etc/docker/daemon.json <<'EOF'
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "50m", "max-file": "3" }
}
EOF
systemctl restart docker
```

**6.2 定时备份**

```bash
crontab -e
0 2 * * * cd /opt/doc-qa-service && docker compose exec -T db pg_dump -U docqa docqa | gzip > /backup/db-$(date +\%F).sql.gz
```

**6.3 探活告警**

```bash
*/5 * * * * curl -fsS http://localhost/healthz > /dev/null || echo "doc-qa 挂了" | mail -s "告警" ops@example.com
```

## 7. 日常巡检清单

**每天：**

- [ ] `docker compose ps` 四个服务都是 running
- [ ] `curl -s localhost/healthz` 返回 ok
- [ ] `df -h /` 磁盘使用率低于 80%
- [ ] 查看是否有 failed 状态的文档

```bash
# 一条命令查失败文档
curl -s "http://localhost/api/v1/documents?limit=100" -H "Authorization: Bearer $TOKEN" \
  | grep -o '"status":"failed"' | wc -l
```

**每周：**

- [ ] 备份文件存在且大小正常（突然变小说明有问题）
- [ ] `docker system df` 看镜像和卷占用
- [ ] 抽查一次问答，确认回答质量没退化

## 8. 性能与扩容

当前架构是单机，瓶颈按出现顺序通常是：

1. **向量检索**：chunks 表超过 50 万行后变慢，检查 hnsw 索引是否建上
2. **PDF 解析**：worker 单进程串行，积压时加 worker 副本即可
3. **数据库连接**：`pool_size=5`，并发高时调大，但别超过 pg 的 `max_connections`

```bash
docker compose up -d --scale worker=3    # 加 worker，SKIP LOCKED 保证不重复处理
```

加 worker 是安全的，因为任务认领用了行锁。加 app 副本需要前面再挂一层负载均衡，当前 nginx 只指了一个 upstream。

## 9. 账号管理

系统没有后台管理界面，管理员操作用数据库直连：

```bash
docker compose exec db psql -U docqa docqa
```

```sql
-- 查看用户
SELECT id, email, role, created_at FROM users ORDER BY id;

-- 重置密码需要走接口，数据库里只存哈希，改不了明文
```

密码重置：让用户在 `/docs` 里重新注册，或由开发同学用脚本生成哈希后 `UPDATE users SET hashed_password='...' WHERE email='...'`。
