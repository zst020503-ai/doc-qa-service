# 评测报告

环境：本机 PostgreSQL 16.15 + pgvector 0.8.6，`EMBEDDING_PROVIDER=mock`、`LLM_PROVIDER=mock`。
测试集 `tests/questions.jsonl`（16 条可答 / 4 条不可答），文档 `samples/` 两份。

**前提：这组数据测的是「无 Key 时回退用的词法哈希向量」，不是真实语义模型的效果。**
它证明链路通、参数怎么定，不证明产品效果。

---

## 一、切分粒度对结果的影响（阈值固定 0.15）

| chunk / overlap | 分片数 | 命中率 | 误拒率 | 编造率 |
|---|---|---|---|---|
| 800 / 100 | 2 | 56.2% | 31.2% | 25.0% |
| 400 / 60 | 4 | 68.8% | 18.8% | 50.0% |
| 300 / 50 | 6 | 81.2% | 18.8% | 50.0% |

分片越细，命中率越高——因为问题通常只对应文档里的一两句话，整篇文档压成一个向量时，
关键句被无关内容稀释了。但细分的副作用是：所有分数整体上移，不该答的问题也更容易过线。

## 二、阈值扫描（chunk 300 / overlap 50）

| threshold | 命中率 | 误拒率 | 编造率 |
|---|---|---|---|
| 0.12 | 93.8% | 6.2% | 50.0% |
| 0.15 | 81.2% | 18.8% | 50.0% |
| 0.18 | 75.0% | 25.0% | 50.0% |
| **0.20** | **68.8%** | **31.2%** | **25.0%** |
| 0.22 | 68.8% | 31.2% | 25.0% |

编造率在 0.18 → 0.20 之间从 50% 掉到 25%，因为有两个不该答的问题（「支持钉钉集成吗」「年终奖怎么计算」）
恰好卡在 0.19 附近。再往上加阈值，编造率不再下降，只是继续误伤正常问题。

**选 0.20**：企业场景里「说不知道」是成本，「说错」是事故。这个点已经是最优折中，
但仍然有 31.2% 的误拒——这是词法向量的天花板，不是参数没调好。

## 三、一次失败的优化尝试（记录在此，避免重复踩）

把 tokenizer 里的中文单字去掉、只保留二元组，想法是减少「支」「持」这类高频字的伪共现。
实测结果：

| threshold | 命中率 | 误拒率 | 编造率 |
|---|---|---|---|
| 0.06 | 100.0% | 0.0% | 50.0% |
| 0.10 | 75.0% | 25.0% | 50.0% |
| 0.15 | 56.2% | 43.8% | 0.0% |

去单字后分数整体下移，同样的阈值下误拒率反而更高，并没有换来更好的区分度。
**结论：回退。** 改向量构造不如直接换模型。

## 四、结论

1. **mock 模式定位**：只用于无 API Key 时跑通链路、验证部署，不作为质量基线。
2. **默认参数**：`CHUNK_SIZE=300`、`CHUNK_OVERLAP=50`、`ANSWER_THRESHOLD=0.20`，
   是当前测试集上的实测最优点，不是拍脑袋。
3. **换真实 embedding 后必须重跑本报告**，阈值不要沿用 0.20——真实模型的相似度分布完全不同。
4. **没有测试集就没有结论。** 20 条问题、10 分钟，就能让「阈值」从玄学变成数据。

## 五、复现

```bash
./scripts/deploy.sh
python scripts/eval_qa.py --base-url http://localhost --report docs/eval-report.md
```

改参数重测的注意点：

- 改 `CHUNK_SIZE` 后必须重新上传文档，老分片不会自动重切（先清空 `documents`）
- **app 和 worker 两个进程都要拿到同一份环境变量**——只给 app 设了切分参数，
  实际切分发生在 worker 里，参数不生效。我第一次扫参数时就踩了这个坑，
  三组不同 chunk 跑出完全相同的指标，才发现测的是同一个配置。
- 每换一个阈值就要重启 app，环境变量不会热加载
